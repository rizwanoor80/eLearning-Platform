## Rulings (owner decisions, numbered, carried across revisions)
R1–R244 carry as last written, except R82 (withdrawn), R145, R146, R236 (superseded).
R245 **CP5 architecture: collection and payouts are separate (owner, 2026-10-20).** Collection: `PaymentGateway` charges, saves cards and refunds; settlement is to the company's UAE bank account; the ledger's `gateway` account is that money. Payouts: never through the collection gateway; a tutor is paid from the company's funds by a **payout method** (new concept, R249) — the method is the tutor's choice among those the admin has enabled for the tutor's `tutor_profiles.country`. In v1 every payout method is **manual**: TrusTutor computes who is owed what, groups it by method, exports a file per method, the admin pays in the bank's or provider's own portal, and records each payment's external reference. API-driven methods (Payoneer, PayPal, Stripe, a bank API) are later drivers behind the same registry, each its own plan. CC records R245 as ADR-030.
R246 **23a — payment gateway registry, holding Stripe (CP5 task; invariant 16).** New `payment_gateways` table and Filament resource: code (`fake`, `stripe` — an enum), name, mode (`test`/`live`), credentials as encrypted JSON entered field by field and shown masked (for Stripe: publishable key, secret key, webhook signing secret), `supports_saved_cards`, `is_active` with a one-active partial unique index. `PaymentGatewayServiceProvider` resolves the driver from the active row; `fake` stays activatable only where `fakeGatewayAllowed()` is true; **switching any row to `live` is refused in code unless an owner-only setting allows it, and that setting is off** (rule 8). With no active row, booking shows a (new) admin-notice page and creates no `payments` row. Proof: the CP5 registry acceptance lines; credentials never in logs, page props or serialisation (18a pattern).
R247 **23b — the Stripe driver, server side (CP5 task; invariants 14, 15).** New `app/Services/Payments/StripePaymentGateway.php` on `stripe/stripe-php`, implementing `PaymentGateway`: `capture` verifies a PaymentIntent the parent already confirmed (R256) for exactly the lesson's amount in AED; `saveCard` attaches the PaymentMethod a SetupIntent produced and returns brand, last four and expiry only; `chargeSavedCard` creates an off-session PaymentIntent with the existing idempotency key (lesson id + attempt), and an `authentication_required` decline is an ordinary failed attempt for `recurring:charge`'s retry and email path. The interface gains `refund(Payment $payment, Money $amount, string $idempotencyKey)` and `verifyWebhook(string $payload, array $headers): bool` (both named in PRD §3 "Pricing and money", the payment-gateway line); `FakePaymentGateway` implements them as it does today's methods. New route `webhooks/payments/{code}` with its own throttle and signature check (the video webhook's shape), idempotent by Stripe event id, handling `payment_intent.succeeded`, `payment_intent.payment_failed`, `charge.refunded` and `charge.dispute.created` (the last records and alerts admins; it changes no lesson state). Proof: every method and webhook against a faked HTTP client, replays are no-ops, no card number or secret anywhere in logs or the database.
R248 **23c — parent card capture and booking checkout (CP5 task).** The parent's card page becomes driver-neutral (list saved cards — brand, last four, expiry — add or replace, remove, an "expiring" notice); for Stripe, cards are added with Stripe Elements (`@stripe/stripe-js`, a SetupIntent, 3-D Secure in the browser); the fake driver keeps its test-card form (`TestCardController`, R100/R107). Booking with Stripe: the browser confirms a PaymentIntent for the quoted price (3-D Secure if the bank asks) **before** `BookLesson` creates the lesson, so no new lesson state is needed; `BookLesson` then calls `capture` with that PaymentIntent and creates the lesson `confirmed` as today. Any page that loads Stripe.js gets it at run time from Stripe (no build-time fetch). If this cannot be done without a new lesson state or edge, 23c parks with the design (R224(3)).
R254 **Stripe is the one collection gateway (owner, 2026-10-20; narrows D-02).** D-02 said "multiple gateways via the registry; Stripe first"; for now there is one: Stripe. The registry stays (invariant 16 keeps credentials and the active driver there) but holds only `stripe` and, outside production, `fake`. Tap or another gateway is a later plan if Stripe cannot onboard the D-04 entity. CC records this in ADR-030 with R245.
R255 **What `app/Services/Payments/*` may change in this cycle.** New `StripePaymentGateway.php`; `PaymentGateway.php` gains exactly the two methods R247 names; `FakePaymentGateway.php` implements them; nothing else in the directory changes. Each change carries the plant-a-failure / see-it-red / revert / see-it-green proof in its PR.
R256 **23d — gateway refunds follow the ledger (CP5 acceptance: "a gateway refund call; webhook replay does not double-refund").** When the ledger records money back to a parent — `LessonSettlement::refundParent` (full) and the parent share of `ResolveDispute` (partial) — an event after commit drives a queued listener that calls the active gateway's `refund` for that amount with an idempotency key derived from the ledger entry, and updates `payments.status` / `refunded_amount` (the cycle 22 advisor note: `ResolveDispute` never did). The ledger stays the source of truth; a failed gateway refund is retried by the queue and listed to admins, never reversed in the ledger. `LessonSettlement.php` may change only to dispatch the event; `ResolveDispute.php` likewise. Proof: full and partial refunds, a replayed `charge.refunded` webhook, a gateway failure then retry, `ledger:verify` green.
R257 **23e — parent receipts (CP5 task).** A receipts page listing each paid lesson: date, tutor display name, learner, amount in AED, the Stripe payment reference, and any refund lines; one printable receipt per lesson. **No VAT line** until D-04 says whether and how VAT applies. No email receipt yet (it follows Postmark).
R249 **23f — payout methods and tutor preference (new).** New admin registry `payout_methods`: code (`bank_transfer`, `payoneer`, `paypal`, `stripe`, `wise` — an enum), name, `is_active`, `countries` (ISO-3166 alpha-2 list; empty = all), and the detail fields it needs from a tutor (bank: the existing `bank_*` fields on `tutor_profiles`; Payoneer / PayPal / Wise / Stripe: the account email). Seeded: `bank_transfer` active for all countries; the others inactive until the admin enables them with countries. A tutor picks a preferred method in Settings (only methods active for their country are offered) and enters its details; the details are encrypted at rest, hidden from serialisation like the bank fields (18a), and shown to admins masked except on the payout export. A tutor with no valid method is listed to admins as "cannot be paid yet" and never blocks anything else.
R250 **23g — tutor earnings with the five buckets (CP5 task; CLAUDE.md "never a single stored number").** The tutor's earnings page computes pending, on hold, available, processing and paid to date from lessons and the ledger, with the definitions written in the page's docblock (pending: confirmed or completed, not yet released; on hold: disputed; available: released to the tutor, not in a batch; processing: in an unpaid batch line; paid to date: in a paid batch line). Until 23h merges, processing and paid to date are 0 and the payout history is empty. Proof: one test per bucket transition, and the sum of the five equals the tutor's lifetime earnings from the ledger.
R251 **23h — payout batches, one file per method (CP5 task, extended by R245).** Admin generates a batch for a period (default cadence `payout_weekday`); it includes only tutors whose available balance is at least `payout_min` (20000 fils by default) and who have a valid method; lines are grouped by method; each method exports its own CSV (bank: account name, IBAN, SWIFT, amount, currency, reference; email methods: email, amount, currency, reference); each line is marked paid only with an external reference (required), or marked failed (back to available). Marking paid writes the `payout` ledger entries (R253) and moves the tutor's money from processing to paid to date. Proof: the CP5 acceptance line on payout batches, a batch with two methods, a failed line, `ledger:verify` green.

R258 **Owner action 13 ruled (owner, 2026-10-21): the combined fix, and the GO for 23h (R253).** One fix round on `cp/23h-payout-batches` (outside the R224 cap, as an owner-ordered round), then one fresh review, then merge:
(1) **Hold back disputable money at the source.** `GeneratePayoutBatch` includes a lesson's released tutor money only once its dispute window has closed: `ends_at` + `OpenDispute::WINDOW_HOURS` (48 h), or `ends_at` + `OpenSuspensionDispute::WINDOW_DAYS` (7 days) for a lesson with a `SettleSuspendedLesson::AUDIT_SETTLED` audit row; disputed lessons never. `TutorEarnings` follows the same rule: released money inside its window is **pending**, shown with the date it becomes available, and moves to **available** when the window closes (R250's "available" is amended to "released, past its dispute window, not in a batch"). The five buckets still sum to lifetime earnings.
(2) **A real transfer is always recordable.** `MarkPayoutLinePaid` never refuses because of the tutor's balance: the `available->isNegative()` refusal is removed. If a balance is ever negative after recording (which (1) should make impossible in normal flow), the line records anyway and admins see a flag on the tutor and the batch; the next batch nets it. The test at `PayoutBatchesTest.php:420` that encodes "mark failed and regenerate" is rewritten to the new rule.
(3) **The Medium goes with it.** Recording a payment no longer coordinates with disputes, so `OpenDispute.php` returns exactly to its `main` version (the 23h branch's change to its lock order is reverted); every lock-order comment the branch added is corrected or removed.
(4) **Proof.** Red on `fb5f6f0` and green after: the reviewer's scenario (paid transfer, then a dispute) records the payment; a lesson released 47 h after its end is not in a batch and is at 49 h; a suspension-settled lesson waits 7 days; earnings buckets per the amended definition; `ledger:verify` green. The `LedgerService::payout()` change on the branch (R253) is unchanged by this round and keeps its plant-a-failure proof.
