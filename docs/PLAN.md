## Rulings (owner decisions, numbered, carried across revisions)
R50 Programme "CP3" authorised (§12). Five sub-cycles in order, each: branch `cp/3<x>-<slug>` from current `main` → PR with the sub-cycle's acceptance boxes as its checklist → fresh-subagent adversarial review → fix loop (cap 2) → merge under the rule → post-merge record on `main` → read-only smoke (`composer test` on `main` with the count quoted; `curl` on `/`, `/login`, `/admin/login`) → next sub-cycle. **Merge rule:** review has no open Medium or High; CI green on the PR head; diff touches only the areas the sub-cycle names plus tests, migrations, seeders, factories, routes and resources; no change to the frozen files named in the boundary above; and for 3c, the backend-dev GO (R55). Any Medium+ finding, any rule miss, or any failure of a money invariant in R52/R53 → PR stays open, STATUS §7 names it "awaiting owner", programme halts. **Stop conditions:** smoke failure; a regression the fix loop cannot clear in two rounds; any High security finding; any money invariant broken; the owner typing `stop`; the session limit (STATUS first). **Resume cap:** 8 automatic continuations, then halt for owner review even if sub-cycles remain. **Board:** STATUS §8 lists the five sub-cycles with state, branch, PR, review verdict, merge hash.
R51 The state machine is declared in full, exercised in part. `LessonStateMachine` declares every state and every edge in DATA_MODEL's diagram, including the CP4–CP6 ones (`in_progress`, `completed`, `no_show_*`, `disputed`, `settled`, `provider_failure`), each guarded and each firing its event, with a test per allowed and per forbidden edge. Only the edges CP3 owns get calling actions this cycle: `pending_payment → confirmed|expired`, `reserved → confirmed|cancelled_payment_failed|cancelled_by_parent|cancelled_by_tutor`, `confirmed → cancelled_by_parent|cancelled_by_tutor`, and the two `cancelled_by_parent → refunded|completed_reported` outcomes. An edge with no CP3 action is reachable only from a test. No other code path may write `lessons.status` — PRD §4 — and a test asserts the column is never written outside the machine.
R52 The ledger lands in CP3, pulled forward from CP5 deliberately: CP3's own acceptance requires a refund path and a tutor-paid path, and those are meaningless as status changes alone. `ledger_entries` per DATA_MODEL (append-only — no update, no delete, enforced by the model and by a test that both throw), with HOLD, RELEASE and REFUND implemented and SETTLE/PAYOUT declared but unused. **Invariant: `sum(amount) WHERE lesson_id = X` = 0 after every transition, asserted in every money test and in a `ledger:verify` command** run in CI. `payments` rows are written by the gateway driver for every capture and refund. Tutor balance buckets are derived, never stored.
R53 Money rules, absolute. Every amount is integer fils through `App\Support\Money` — no float, no `round()` on money, no `*` or `/` on a raw integer outside the value object; a test greps the diff areas for `price`-typed floats. `TutorProfile::trialPrice()` is the ONE place a trial price is computed; the onboarding preview's `100 − pct` rounding is deleted and replaced by a call to it, with a test proving preview and booked price agree across the whole band table including an odd-fils case. Frozen onto the lesson row at creation and never re-read from settings afterwards: `price`, `commission_pct`, `commission_amount`, `tutor_amount`, `cancel_window_hours`, `student_grace_min`, `tutor_grace_min`. A test changes all seven settings after booking and asserts the lesson's outcome is unchanged (CP3 acceptance box 5). `commission_amount + tutor_amount = price` exactly, with the remainder fil going to the platform, tested at a price that does not divide evenly.
R54 Deletion decided (the open CP2 question). A learner is soft-deleted only when they have no lesson in a non-terminal state; the attempt is refused with a message naming the blocking lessons. A user is never hard-deleted: deletion anonymises (name, email, phone replaced with a tombstone, auth credentials cleared, sessions and tokens revoked) and leaves `lessons`, `payments` and `ledger_entries` intact with their foreign keys, because financial history must survive the person. Soft-deleted learners stay visible on past lessons. Admin action, audited; not exposed to parents in CP3.
R55 Sub-cycle 3c halts for the backend developer before merge — the one human gate this programme. It is the sub-cycle that computes and freezes money, so the PR waits with the review attached until the owner relays the GO. 3a, 3b, 3d and 3e self-merge under R50. If the backend dev is unavailable, the owner may give the GO himself and it is recorded as such.
R56 Booking limits come from settings, not constants: `booking_min_lead_hours` (seeded 12) and `booking_max_days` (seeded 30) drive `SlotCalculator` and `BookLesson` alike, and PRD §4's figures are those seeds, not hard-coded rules. `BookLesson` re-derives from `SlotCalculator` at booking time and re-checks `TutorProfile::bookable()` and permit validity then — search-time validity proves nothing (the carried CP2 item). The permit cap from R34 applies at booking as well as at offer.
R57 Docs authorised this cycle: DATA_MODEL.md v1.4 (any column CP3 actually adds or changes, with a deviation note wherever the build differs from v1.3), CHECKPOINTS.md (CP3 boxes as they close; CP4's carried items), DECISIONS.md (ADR-008 ledger pulled into CP3 per R52; ADR-009 deletion policy per R54).
