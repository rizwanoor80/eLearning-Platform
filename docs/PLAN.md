## Rulings (owner decisions, numbered, carried across revisions)
R113 **Cycle 06 scope.** Three steps: 6a the single-booking screen (R114), 6b the advisor-model measurement (R115), 6c rehearsal deploy and END (R117). Why now: it is the last missing piece of the PRD §2.2 journey that the fake gateway can carry, it unblocks trial → weekly slot on rehearsal for the team, and it needs no D-02/D-04/D-09. Nothing from CP5–CP8 is pulled forward.
R114 **Single-booking screen — the planner's recommendation, adopted.** (a) Entry: on `tutors/Show.vue` each "Next available slots" item becomes a link for a signed-in parent to `GET tutors/{tutor}/book?starts_at=<UTC ISO>`; a guest is sent to login and returned to the same URL; tutors and admins see the slots as plain text. (b) Page `lessons/Book.vue` (thin controller, Form Request, Policy): the chosen slot shown in the parent's timezone; learner picker limited to the parent's own non-deleted learners, with a link to add one when there are none; curriculum and subject picker limited to that tutor's `TutorSubject` rows, preselecting the learner's curriculum when it matches; "Trial lesson" or "Lesson" and the price shown **as the server computes them** — the same code path `BookLesson` uses (`TutorProfile::trialPrice()` / the rate), never recomputed in the browser; the client never sends `type` or price (invariant 12). (c) `POST lessons` calls `BookLesson` unchanged. Success → redirect to the learner's page with "Lesson confirmed"; the 3e confirmed emails fire as they do today (verify, add nothing). `BookingException` → back to the page with its message and the slot list refreshed; `PaymentCaptureException` → back with a plain "Payment did not go through" message and whatever lesson state 3c already leaves (no new handling). (d) The booking window (≥12h, ≤30 days), on-the-hour and overlap rules are already enforced through `SlotCalculator` inside `BookLesson`; the page validates nothing of its own beyond shape, and a stale or hand-edited `starts_at` must fail through the action. (e) `TestModeBanner` on the page; the button reads "Confirm and pay" with the banner explaining no real card is charged; no card form (CP5). (f) Match path: wherever match suggestions already link to a tutor profile, they now reach this flow; no new match work. (g) Tests, at least: guest redirect and return; parent books a first lesson → `trial`, discounted price, `confirmed`, HOLD, `LedgerService::sum()===0`; second booking with the same tutor → `regular`, full price; another parent's learner → refused; unbookable tutor → error; slot inside 12h, beyond 30 days, off the hour, or already taken → error and nothing created; tutor and admin → 403; a tampered `type`/price field is ignored; the displayed price equals the frozen `lessons.price`; banner prop present only where R107 binds the fake gateway; slot links on the profile for a parent only.
