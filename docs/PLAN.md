## Rulings (owner decisions, numbered, carried across revisions)
R1–R272 carry as last written, except R82 (withdrawn), R145, R146, R236 (superseded).
R273 **26a — erasure has an entry point (owner, 2026-10-22).** (1) **Admin "Erase account"** on the Filament Users resource (`app/Filament/Resources/Users/UserResource.php`), admin-only, with a confirmation that names the account and states what is erased and what is kept; it calls the existing `AnonymizeUser` unchanged in its rules (it already refuses non-admins, admin accounts and accounts with open lessons; R268 keeps bank details while money is owed) and shows its refusal message as the result. (2) **"Request account deletion"** for parents and tutors in their Settings: it never erases anything itself; it creates a request in a new admin queue (new table `account_deletion_requests`: user, requested_at, status `open`/`erased`/`declined`, handled_by, handled_at, admin note) and acknowledges the request on screen and by mail to the account's own address. The queue offers "Erase" (runs the action in (1)) and "Decline" with a note mailed to the user (for example, money still owed or a lesson still open). A user with an open request sees it in Settings and cannot file a second one. Learners have no logins (invariant 7), so a parent's request covers their learners through the existing erasure rules. Proof: both paths, every refusal, the queue states, no PII in audit rows or logs.
R274 **26b — payout copies are erased with the tutor (Owner action 23, option 1, owner 2026-10-22).** When `AnonymizeUser` erases a tutor, every **paid** `payout_batch_lines` row for that tutor has its `details` copy erased; amount, method, currency, `external_reference` and `paid_at` stay (who was paid what, when, and the bank's reference — what accounting needs). Unpaid lines keep their copy until the admin's manual decision under R268, then follow the same rule. `details` is `text` and not nullable today: CC makes it nullable (R280) or writes a fixed erased marker — chosen with the advisor — and the export refuses a line whose details are erased. How long payment records must be kept is a counsel question; nothing here deletes a payout line.
R275 **26c — production pre-flight and clean seeding (CP8 "Production hardening": `.env` review, seed data removed).** (1) New read-only artisan command `ops:preflight` (new): checks the environment it runs in and prints one PASS/FAIL line per check, never a value: `APP_ENV=production`, `APP_DEBUG` off, `APP_URL` https, `APP_KEY` set, session and cookies secure, the mailer is not `log`/`array`, the queue is Redis with Horizon configured, the scheduler entry expected, the `fake` payment gateway and the `fake` video provider not active, an active payment gateway row present (its mode reported, `test` or `live`), the webhook signing secret present (presence only), `config/trustedproxy.php` consistent with how the app is reached (R130: empty unless a load balancer fronts it), no demo accounts present (the demo seeders' known emails/markers), storage link present, `ledger:verify` OK. Exit code non-zero on any FAIL. On rehearsal it is expected to FAIL the production-only checks; the test suite runs it against a faked production config. (2) **Seeding:** prove with a test that `DatabaseSeeder` under `APP_ENV=production` creates only reference data and the one admin (`AdminUserSeeder`) and no demo user, tutor, learner, lesson or slot (today the demo seeders run only for `local` or by hand); if that is already true, the test is the deliverable.
R276 **26d — error tracking, off until the owner adds a token.** Add one error tracker: the planner's default is Sentry (`sentry/sentry-laravel`; it needs only an environment value and no server daemon; it must have a git source so the cloud install and `ComposerLockPortabilityTest` pass — if it does not, CC picks Flare (`spatie/laravel-flare`) on the same terms and logs why). It is inert without its DSN, never sends from `local`/`testing`, and scrubs request bodies, cookies, the `Authorization` header, card and bank fields and any `*_secret`/`*_key`/`*token*` value before sending; `ops:preflight` reports whether the DSN is present. The owner creates the account and enters the DSN on the server later.
