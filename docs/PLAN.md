## Rulings (owner decisions, numbered, carried across revisions)
R1–R282 carry as last written, except R82 (withdrawn), R145, R146, R236 (superseded).
R283 **v2 scope: TrusTutor SaaS (owner, 2026-10-24; ADR-031; PRD §13 written by CC from this ruling, PRD §11 D-rows untouched).** (1) A **tenant** is one TrusTutor instance: own database, own brand, legal entity, settings, pages, tutors, parents, payment gateway keys, video rooms (on TrusTutor's Daily account, never shown), payouts. (2) **Pricing is per lesson, billed monthly in arrears** on one Stripe invoice per tenant: standard lesson $1; later tiers (recorded $2.50 with 14-day streaming-only retention and parental consent; transcript add-on $1) are programme-later; custom domain $10/month or $100/year; a $5/month minimum waived against lesson charges; card on file at signup. (3) **Lesson money never touches TrusTutor:** each tenant collects through its own gateway and pays its own tutors (R245 per tenant). (4) **Public by rule:** tutor profiles (display name, subjects, rating) and, later, tutors' anonymised explanations are public across the network; it is a condition in the tenant terms and the tutor agreement; a centre that refuses is not a customer. (5) **Tenant number one** is the v1 marketplace, ranked and treated like every other tenant; the operator never uses tenant data to compete (fairness rule, in the terms). (6) Learners never have logins (invariant 7) in any tenant; the AI and coverage features, when built, live in the parent portal. (7) The 3-D Secure, recording-consent and children's-data questions are counsel's; nothing in v2 ships recording or AI before counsel answers.
R284 **28a — tenancy spike (one cycle, decides the mechanism; no product change).** With the advisor: (1) choose between the `stancl/tenancy` package (archtechx/tenancy; must support Laravel 13 and PHP 8.4, have a git source for the cloud install, pass `ComposerLockPortabilityTest`) and a hand-rolled minimal tenancy (a central `tenants` + `tenant_domains` table, a middleware that resolves the tenant from the host and switches the `pgsql` connection to the tenant's database, a tenant-aware job middleware); the spike builds the thinner one that works and records why. (2) Prove on a throwaway branch: two tenant databases on one PostgreSQL, the full 3631-test suite green against a tenant connection, a request on `a.test` and on `b.test` reading different databases, a queued job and a scheduled command running against the right tenant. (3) Measure: per-tenant database creation time, migration-all-tenants time for 2 and 20 tenants, connection pooling needs (PgBouncer or Laravel's own). (4) Deliverable: ADR-032 "tenancy mechanism" with the measurements and the package or design, and `docs/runbooks/tenancy.md` (new) skeleton. Code from the spike may be kept only if the review passes; else 28b starts clean from the ADR.
R285 **28b — tenancy core.** Central database (new connection `central`; central migrations under `database/migrations/central/`): `tenants` (id, slug, name, plan, status `active`/`suspended`/`closed`, created_at), `tenant_domains` (tenant, host, is_primary, verified_at, tls_issued_at), `tenant_admins` (the signup user), `tenant_terms_acceptances` (version, accepted_at, ip). Tenant resolution by host on every web request and webhook; `APP_URL`, mail `from`, asset and signed-URL generation use the tenant's primary host. `php artisan tenants:create {slug}` (new) creates the database, runs the v1 migrations, seeds reference data (curricula, year groups, subjects, price bands, document types, settings, pages, content blocks — never demo data), and creates the first admin. `php artisan tenants:migrate` (new) migrates every tenant and reports per tenant; a failure on one tenant stops and names it. The tenant database schema is the v1 schema, unchanged. Proof: two tenants on rehearsal's PostgreSQL in tests, the whole suite green under tenancy, isolation tests (a user of tenant A cannot authenticate or read on tenant B's host; signed URLs from A fail on B).
R286 **28c — tenant runtime.** Every queued job carries its tenant and runs against it (Horizon unchanged; one queue); every scheduled command in `routes/console.php` (`tutors:check-permits`, `lessons:expire-unpaid`, `recurring:generate`, `recurring:charge`, `lessons:send-reminders`, `lessons:create-rooms`, `lessons:close-rooms`, `lessons:settle-ended`, `lessons:auto-release-reports`, `video:prune-webhook-deliveries`, `payments:retry-refunds`, `ops:record-ledger-check`) runs once per active tenant with `onOneServer()`/`withoutOverlapping()` kept per tenant, and a failure in one tenant does not stop the others; file storage (documents, receipts, exports) under a per-tenant prefix on the private disk; cache and session keys prefixed per tenant; Stripe and Daily webhooks routed to the tenant by host (the webhook URL a tenant registers is on its own domain); `/ops/status` per tenant, and a new central `/ops/fleet` (new; central token) listing every tenant's status; `ops:preflight` runs per tenant and centrally. Proof: the per-tenant scheduler loop with one failing tenant; a webhook for A delivered to B's host is rejected; storage and cache isolation.
R287 **28d — domains and Caddy.** Each tenant gets `{slug}.trustutor.com` at creation. Custom domains: the tenant adds a domain in its admin, proves it by a DNS TXT record or a CNAME to its subdomain, and it becomes active once verified. Caddy fronts the app for TLS: an on-demand-TLS **ask endpoint** (new, `GET /internal/tls/ask?domain=`, central, unauthenticated but answers only yes/no, rate-limited) returns 200 only for verified tenant domains and the platform's own hosts, so Caddy issues certificates only for domains the platform knows; nginx stays behind Caddy on Forge (the owner sets Caddy up by `docs/runbooks/tenancy.md` §Caddy, written here: install, the on-demand block with the ask URL, HTTP→HTTPS, proxy to nginx, the one DNS record a tenant needs). Proof: ask endpoint yes/no, verification flow, a domain cannot be claimed by two tenants, a suspended tenant's domains answer no.
R288 **28e — signup, onboarding and super-admin.** Public signup at trustutor.com (new): name, email, password, slug, acceptance of the tenant terms (R283(4), (5) stated in plain words) with the version recorded, card on file (Stripe Checkout in setup mode on the central Stripe account; the card token stored centrally, never the number); then `tenants:create` runs and the new admin lands in its own admin on `{slug}.trustutor.com` with an onboarding checklist: brand (name, logo, colours), legal entity and contact, legal pages from the platform templates (marked DRAFT until edited), its own Stripe keys, its first tutor. **Super-admin** on `ops.trustutor.com` (new host; Filament panel in the central database; its own admin users, 2FA required): tenants list with status, plan, domains, lesson counts, last activity; suspend/reinstate (a suspended tenant's sites show a maintenance page); "open as support" into a tenant's admin with an audit row per use and a banner; invoices (R289). No tenant data is aggregated for anything but billing and the fleet status.
R289 **28f — lesson metering and billing.** A central `lesson_usage` table (new) records one row per lesson that reaches `completed`, `completed_reported` or a paid no-show outcome in any tenant (tenant, lesson id, ended_at, tier `standard`), written by the tenant's settlement path after commit; refunds and provider-failure lessons are not billed. Monthly, Laravel Cashier (Stripe Billing, central Stripe account) raises one invoice per tenant: lessons × $1 (plus the custom-domain add-on; the $5 minimum applied as a floor), paid from the card on file; failed payment → dunning emails (Cashier's) → after 14 days the tenant becomes read-only (no new bookings; existing lessons run; admin sees the reason) until paid; the invoice shows the lesson count, never learner data. `tenants:bill` (new) is idempotent per tenant per period. Tenant number one is billed like the others (the invoice goes to the operator's own account; it must exist, and it proves the path). Proof: a period with 7 lessons, a refund, a provider failure and a domain add-on bills 7 × $1 + $10; a $0-lesson month bills $5; a second run bills nothing; the read-only state and its lifting.
R290 **Central database and rehearsal migrations (rule 8, named).** A second PostgreSQL database `trustutor_central` on rehearsal's server, created by the owner from Forge (Owner action, before 28b deploys) and named in the environment; central migrations run through push-to-deploy like tenant ones; R213 shows `pending 0` for both. Production is untouched.
