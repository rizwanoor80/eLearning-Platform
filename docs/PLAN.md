## Rulings (owner decisions, numbered, carried across revisions)
R1–R258 carry as last written, except R82 (withdrawn), R145, R146, R236 (superseded).
R259 **24a — booking capture is robust (23c notes (a), (b), (c), (d); 23b notes on the `BookLesson` race, outage and `amount_mismatch`, and attempts older than 24 h).** (1) `StripePaymentGateway::capture()` catches Stripe API and connection errors and reports a retryable outcome; retrying the same booking succeeds without a second hold or charge (proof: an injected connection error on the first try, success on the second, one PaymentIntent). (2) A booking whose payment was captured but could not be confirmed (`PaymentCapturedUnverified`) is refunded automatically through the gateway, recorded so `ledger:verify` and the payment row agree, alerted to admins, and the parent's "we will refund you" message is then true; CC designs the recording with the advisor and does not change `LedgerService.php` (if that is impossible, this item parks with the design and the rest of 24a ships). (3) A double click or repeated submit makes one hold, not two (a per-attempt key the browser sends and the server enforces). (4) A `payment_intent.succeeded` webhook with no `payments` row raises an admin alert (deduplicated). (5) A pending payment left with a null `gateway_ref` by the `BookLesson` race is either prevented or reconciled, so `ledger:verify` reports no false positive. (6) An attempt older than 24 h first looks up an existing PaymentIntent before creating one.
R260 **24b — refunds have a real state (23d notes (a)–(f), (j)).** New `payment_refunds` table (new): one row per gateway refund attempt — payment, ledger entry it follows, amount in fils, idempotency key, gateway refund id, status (`requested`, `succeeded`, `failed`), failure reason, timestamps. 23d's `raw_response.refunds` / `refund_failures` JSON is migrated into it once (forward-only, additive: the JSON stays); receipts and the admin lists read the table. An admin action re-queues a failed refund (replaces "list only"). `charge.refunded` webhooks for refunds not made by the platform (a Stripe-dashboard refund) are reconciled into the table and alerted, never applied to the ledger automatically. The `NeedsReview` path in `ChargeReservedLesson` (about lines 274–283) refunds automatically like (2) of R259. The Stripe client's timeout is set below the Horizon job timeout (60 s, `config/horizon.php`) so a job never dies mid-call. Proof: full, partial, failed-then-retried and dashboard-made refunds; `ledger:verify` green.
R261 **24c — a parent can remove a saved card (23c note (g)).** New nullable `payment_methods.removed_at` (new); the unique index on `payment_methods.account_user_id` becomes a partial unique index where `removed_at` is null, so one live card per account remains the rule; Remove detaches the card at the gateway (`StripePaymentGateway`) and sets `removed_at`; old payments keep their foreign key to the removed row. Removing the card behind an active weekly slot is allowed only after a confirmation that says the next auto-charge will fail until a new card is added. Proof: remove, re-add, history intact, the weekly slot's next charge fails cleanly with the existing failure email.
R262 **24d — the booking page (23c note (e)).** The Payment Element mounts once however fast the learner changes; learner and subject selects are disabled while a payment is in flight; a redirect-based 3-D Secure return is handled (the `return_url` path resumes or explains), not only `redirect: 'if_required'`. Proof: browser-level tests where the suite has them, otherwise component tests plus one manual-check note in STATUS for the owner on rehearsal.
R263 **24e — payout hardening (23h notes (b)–(e); 23f notes).** (1) Each payout batch line stores a snapshot of the tutor's method and the details used (encrypted, hidden like the bank fields), so a later change of preference cannot alter what a past line paid. (2) `OpenSuspensionDispute` takes the same lock order as `OpenDispute`; `GeneratePayoutBatch` reads the tutor's user row under the users-then-profile order (18d). (3) The payout actions check the admin role themselves, not only through Filament. (4) The export is safe for a bank upload: values that would start a spreadsheet formula (`=`, `+`, `-`, `@`) are refused at input time on the payout details, so the export carries no `'` prefix to the bank. (5) An anonymised tutor with money still owed is not dropped: generation flags the amount for admins ("owed to an anonymised account — decide manually") and keeps it out of batches. (6) Tests for netting a negative balance in the next batch, the flag absent when the balance is not negative, and settle-then-pay end to end through the real actions.
R264 **24f — test hygiene.** `YearGroupFactory` cannot collide with seeded `Year N` labels (the 2026-10-20 `DatabaseSeederTest` flake); the 23g test gaps — `lifetime()` proved independently of the buckets, nav visibility, the `payout_problem` null path, tests that move lessons through the real actions instead of setting statuses.
R265 **Rehearsal migrations authorised for this cycle (rule 8, named).** The migrations of 24b (new table, data copy from JSON), 24c (new column; the `payment_methods.account_user_id` unique index replaced by a partial unique index) and 24e (new encrypted snapshot columns on payout batch lines) may run on trustutor-rehearsal through push-to-deploy; R213 must show `pending 0` after each deploy.
