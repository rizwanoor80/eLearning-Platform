R179 **Booking lead time is the tutor's choice (owner, 2026-10-07).** PRD §4's fixed "≥ 12 h before start" becomes a per-tutor setting `min_lead_hours` on `tutor_profiles`, chosen from an admin-managed list of allowed values (settings group `booking`: `lead_time_options`, default `0,4,8,12,24`; `allow_immediate_booking`, default **true on local, testing and rehearsal, false on production** — seeded per environment, and the admin can change it). `0` means "immediately": the slot must simply be in the future and inside the tutor's availability. The tutor sets it on the Profile page (default 12 if unset, so existing tutors are unchanged); the demo-tutor seeder sets 0 for every demo tutor so rehearsal tests run same-day. Search and the profile page show the tutor's lead time ("Book from 4 hours ahead" / "Book right away"). Booking validation, slot generation (`next available slots`) and the weekly-slot first-lesson check all read the tutor's value instead of the constant; the 30-day horizon is unchanged. **Cancellation rule unchanged** (PRD §4: a parent cancelling < 24 h before gets no refund). When the chosen slot starts within 24 h, the booking page states before payment: "This lesson starts within 24 hours, so it cannot be cancelled for a refund." — stated to the owner once as the trade-off and accepted. Tests: lead 0 / 4 / 24 accept and refuse at the boundary (minute precision, tutor timezone); `allow_immediate_booking=false` hides and refuses 0 even if a tutor had chosen it (falls back to the smallest allowed value); the within-24h notice appears exactly when the rule applies. ADR-025; PRD §4 row amended by CC and quoted in VERIFICATION.
R180 **Webhook visibility (planner, 2026-10-07; closes the blind spot behind PLAN item 4).** `VideoWebhookController` records **every** delivery that passes the signature check, including ones `parseWebhook()` ignores: a new `video_webhook_deliveries` table (provider, received_at, http_status we returned, event type as sent, event id if present, body length, a list of top-level keys and `payload` keys — never the body, never a token) written in the same request, before the existing `video_webhook_events` logic; ignored deliveries also `Log::info('video.webhook.ignored', [...])` with the same fields. A read-only artisan command `video:webhooks --since=24h` prints the last deliveries and stored events (no payloads) so CC can answer "did Daily call us" from the allow-listed shape; the planner adds that command to CLAUDE.local.md's read-only list (owner's file; CC asks in STATUS if it is missing).
