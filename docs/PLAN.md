R95 **A weekly slot's price is agreed once.** `CreateRecurringSlot` computes the regular price from the tutor's current rate, band-validates it (invariant 6 — creating the slot is the booking) and freezes it on the slot as `recurring_slots.price` (fils). Each generated lesson copies the slot's price and freezes its own `commission_pct`, `commission_amount`, `tutor_amount`, `cancel_window_hours` and grace minutes from settings at generation (invariants 6 and 11, read literally: policy is copied when the lesson row is created). A later tutor-rate or band change affects new slots only; a tutor who wants a new price ends the slot with notice. Weekly lessons are always `regular`, never `trial`.
R96 **Trial prerequisite and admin override.** A slot requires the learner–tutor pair to have a trial lesson in `completed`, `completed_reported` or `settled`, or an admin override. Until CP6 wires completion no live lesson reaches those states, so on rehearsal slots are admin-created: a Filament "Create weekly slot" action on a learner–tutor pair that bypasses only the trial check (every other validation runs, including the saved card), audited with the admin's typed reason. Parent-facing entry points still render and, when the check fails, say the weekly slot becomes available after the trial is completed.
R97 **Time and calendar.** A slot is stored as weekday + `start_time` in the tutor's timezone (the availability timezone), on the hour. Each occurrence is converted on its own date, so it is DST-correct and its UTC time (and a parent's local time) can move across a DST change; tests pin Asia/Karachi → a Dubai parent (the CHECKPOINTS box) and Europe/London across the late-October change. An active **or paused** slot blocks its weekday/time in `SlotCalculator` for every date from `starts_on` up to its end (`ends_on` or `end_effective_on`), beyond `generated_until`. Creation validates against the tutor's availability rules and existing future lessons at that moment; afterwards the slot is a standing reservation — later availability-rule edits neither end nor skip it (only `blocked` exceptions, colliding lessons and tutor unavailability cause skips, R98). `starts_on` respects `booking_min_lead_hours`; `ends_on` is optional.
R98 **Generation and skips.** `recurring:generate` runs daily (scheduler, `onOneServer`, `withoutOverlapping`) and extends each `active` slot to today + `recurring_horizon_weeks`, one transaction per slot, with a DB unique index on `lessons (recurring_slot_id, starts_at) WHERE recurring_slot_id IS NOT NULL` as the idempotency backstop. An occurrence that collides with a non-freeing lesson (either CP3 constraint) or a tutor `blocked` exception, or whose tutor is not `bookable()` (suspended, permit expired), is not generated: it is written to a new table `recurring_slot_skips (id, recurring_slot_id, starts_at utc, reason enum lesson_collision|tutor_blocked|tutor_unavailable, notified_at, timestamps, unique (recurring_slot_id, starts_at))` and the parent is emailed once per row (`notified_at` makes the email idempotent). The slot stays active on a tutor-unavailable skip; the admin decides. Paused and ended slots generate nothing. Each generated lesson gets `next_charge_at = starts_at − recurring_charge_lead_hours` (setting read at generation), so 4e needs no backfill.
R99 **Ending and pausing.** Parent ends: immediate; every future `reserved` lesson → `cancelled_by_parent` (free, no ledger, no strike). `confirmed` lessons are **not** auto-cancelled: they stay, and the end screen lists each with its own §4 cancel action and consequence, so ending a slot never moves money by itself. Tutor ends: `end_effective_on` = today + `recurring_tutor_end_notice_days` (setting read at that moment); `reserved` lessons after `end_effective_on` → `cancelled_by_tutor` with no strike; lessons inside the notice period stay and follow §4 if the tutor skips one (strike only inside 24h — CP3's `SkipLesson` rule). Admin end: as parent end, actor recorded. Pause (`admin`, or `payment_failed` from 4e): generation stops, and every future `reserved` lesson is cancelled free as `cancelled_by_parent` with `cancelled_by_user_id` = the actor (admin or null for the system) and `cancel_reason` = `slot_paused` — the state machine has no admin-cancel state and is frozen (R94), so the actor and reason carry the truth. Resume refills through generation from today. **Advisor consultation required on this mapping before 4b's first edit; if the advisor objects, CC halts with an Owner action rather than inventing a state.** The active-slot unique index is replaced (forward-only migration) by one on `(tutor_profile_id, weekday, start_time, timezone) WHERE status IN ('active','paused')`, so a paused slot keeps its place and resume can never collide; two parents racing the same weekday/time are refused at the DB and translated to a clean message.
R100 **Saved card on the fake gateway.** `payment_methods` per DATA_MODEL (one per account; token, brand, last four, expiry, status; never a card number — invariant 15). `PaymentGateway` gains `saveCard` and `chargeSavedCard(Lesson, Money, PaymentMethod, string $idempotencyKey)`. `FakePaymentGateway::saveCard` returns a fake token chosen from two test cards picked from a list, never typed digits: "Test card — always succeeds" (last four 4242) and "Test card — always declines" (last four 0002); the charge outcome follows the token. The parent "Add a card" page is a fake-driver page: it says "Test mode — no real card is charged", has no card-number or CVC field, and refuses to render or submit when `APP_ENV=production` (rehearsal reports `rehearsal`). CP5 replaces the page with the real driver's capture. A slot cannot be created without an `active` card on the account.
R101 **Auto-charge (4e).** `recurring:charge` runs hourly (`onOneServer`, `withoutOverlapping`): every `reserved` lesson with `next_charge_at <= now()` whose slot is `active`, row-locked and re-checked under the lock. Idempotency key `lesson:{id}:attempt:{n}` — derived from the lesson id as invariant 14 requires, with the attempt number so a real gateway's cached result for a failed attempt cannot block the retry; `n` advances only after an attempt's result is recorded, so running the job twice is a no-op. **Success:** in one transaction, `payments` row captured, `reserved → confirmed`, HOLD through `LedgerService`, slot `consecutive_charge_failures` reset to 0; parent emailed a payment confirmation (not a tax receipt — D-04). **Failure:** a `failed` payments row for that attempt, `charge_attempts` +1, `next_charge_at = starts_at − next offset` from `recurring_retry_hours` ([36, 24]), parent emailed with the retry time. **After the last retry fails:** `reserved → cancelled_payment_failed`, slot counter +1, parent and tutor emailed; at `recurring_pause_after_failures` (2) the slot pauses (`payment_failed`) per R99 and parent and admin are emailed. Replacing the card on a `payment_failed`-paused slot offers the parent a one-click resume. **`payments` uniqueness (the R78 item, decided):** `lesson_id UNIQUE` is replaced by `attempt_no` with `unique (lesson_id, attempt_no)` and a partial unique on `(lesson_id) WHERE status NOT IN ('failed')` — one live payment per lesson; failed attempts are their own rows. `BookLesson`'s idempotency guard must still hold on the partial index; a red/green test proves a second capture on one lesson is refused at the DB. `ledger:verify` green on a local seeded DB with charged, failed, cancelled and paused-slot weekly lessons.
