## 1. Subjects row overflow (R187b) — manual check

**There is no browser test tool in this repository (no Dusk, no Playwright) and Claude Code does not
drive a browser**, so this change is verified by reading the layout, not by a screenshot. The
owner or the UI developer should look at it once; the checks are below.

What was wrong: each subject row was `grid grid-cols-4`, four `<select>`s side by side with no
`min-width: 0`. Long option text ("Cambridge IGCSE", full year-group labels) sets a select's minimum
width, so the grid grew past the card and the row overflowed on narrow screens.

What changed (`resources/js/pages/tutor/Onboarding.vue`, subjects form):

- Row: `grid-cols-1` on phones, `sm:grid-cols-2` from 640px up (two selects per line, not four).
- Each cell and each select: `min-w-0` and, for the select, `w-full`, so a long option is clipped
  inside its cell instead of widening the row.
- The legacy-match note and the Remove button span both columns from `sm` up (`sm:col-span-2`).
- The form keeps its `max-w-2xl` cap.

Manual check to run (Required / Optional tags are on the same page, so look at them too):

| Width | Expect |
|---|---|
| 1280px | Curriculum and Subject on one line, From/To year group on the next; nothing wider than the form; no horizontal scrollbar |
| 768px | Same two-per-line layout |
| 375px (phone) | One select per line, full width; long year-group labels cut off inside the select, not past the card |
| Any width | A row with the legacy-match note: the note and **Remove** sit on their own full-width lines |

Owner action recorded in STATUS §7: open the page at 1280px and at phone width once.

## 2. The 409 finding (R187a)

**Finding.** The tutor saw a bare "409 conflict" page. Two causes, both real:

1. The app raises `abort(409)` itself in several places (a step that is locked once the profile is
   submitted, a second "submit for review", the rate step before any subject exists). On a form
   submit that rendered the framework's error page instead of a message on the page the tutor was on.
2. The Inertia *asset-version* 409 (a deploy happened while the tab was open) is middleware, not an
   exception. The Inertia client already reloads on it, so it was not the cause and is left alone.

**Fix** (`bootstrap/app.php`): one render callback for an `HttpExceptionInterface` with status 409
on a non-safe, non-JSON request. It flashes an error toast and redirects back (fallback: home).
Nothing else is caught: 403, 404, 500 and any other exception reach the normal handler and the log
(`tests/Feature/Tutor/ConflictHandlingTest.php`, "does not turn other http errors into a redirect").
A JSON request and a GET still get a real 409.

**Messages the tutor now sees** (toast, error style):

| Where it comes from | Message |
|---|---|
| Any `abort(409)` with no text | That could not be done because the page was out of date. Please check it and try again. |
| Rate step with no subject chosen (`SetTutorRate`) | Add at least one subject before setting your rate. |
| Second "submit for review" | Your profile has already been submitted for review. |
| A step edited while the profile is with the review team | Your profile is with the review team, so this section is locked for now. |

The other 409 messages in the onboarding controller are unchanged and now reach the tutor on the
page instead of an error page.

## 3. "No lessons today" (R187c) — cause and what is not proven

**Cause found.** `TutorDashboardController` listed today's lessons with
`whereIn('status', [reserved, confirmed, in_progress])`. A lesson leaves `in_progress` when it ends
(completed, reported, settled, a no-show, disputed), so a 14:00 lesson disappeared from "Today" as
soon as it was taught and the page said "No lessons today" while the day's timeline showed it. The
list is now "everything that stands" — every status except `pending_payment` and the slot-freeing
ones (`expired`, the cancelled statuses, `refunded`), via `notOnTodaysList()`. The status badge also
shows `in progress` rather than `in_progress`.

**Not proven.** The owner's exact lesson is not in the repository, so this is the cause the code
and the tests show, not a reproduction of their screen. The new tests in `tests/Feature/Lessons/TutorDashboardTest.php` cover a taught lesson in each
after-lesson status, a cancelled / expired / refunded one left off, and a 14:00 lesson for a tutor
whose zone is behind UTC; an unpaid lesson staying off the list is covered by the existing test in
that file. If the owner still sees "No lessons today" with a lesson on screen elsewhere, the next
suspect is the day window (`$todayStartsUtc` / `$todayEndsUtc` from the tutor's own `timezone`) for a
zone the tests do not use; say so in the reply to this cycle.
