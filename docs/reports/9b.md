# 9b — Disputes (R150)

Cycle 09, sub-cycle 9b, branch `cp/9b-disputes`. Scope: PRD §2.10's dispute lifecycle end to end —
account-holder open within 48h, escrow-release pause while open, admin two-dial resolution through
`LedgerService::settle()`, tutor/admin notifications on open, a Filament `Disputes` queue, the
`disputed`/`settled` state-machine edges and their tests, and a seeded-DB `ledger:verify` proof with
resolved disputes.

## CP8 dispute acceptance box — status

`docs/CHECKPOINTS.md`'s literal box (quoted verbatim):

> Dispute on a lesson in `completed` blocks auto-release; two-dial resolution leaves ledger
> zero-sum; trial dispute defaults to 100% refund.

**Met, mapped clause by clause:**

| Clause | Evidence |
|---|---|
| "blocks auto-release" | `AutoReleaseLesson`'s query is scoped to `status = Completed` ([`app/Actions/Lessons/AutoReleaseLesson.php:60`](../../app/Actions/Lessons/AutoReleaseLesson.php:60)); once `OpenDispute` moves the lesson to `Disputed` it drops out of that query. Proven directly: `tests/Feature/Lessons/AutoReleaseReportsTest.php::leaves a disputed, an already-reported and a not-yet-due lesson alone`. |
| "two-dial resolution leaves ledger zero-sum" | Unit-level: `tests/Feature/Ledger/LedgerServiceTest.php`'s dial-matrix dataset (`it('computes the exact r/t/d fils and final per-account balances at every PRD default, 0/0, 100/100 and a rounding case, whether or not the lesson was already released', ...)`, line 375 — 5 cases including the reversal-aware, already-released path) and its dedicated `it('settles a negative platform delta as goodwill', ...)` test (line 347, the `Goodwill`/`platformDelta < 0` branch — see Known limits, this branch is not otherwise exercised end-to-end). Whole-system proof on a non-empty, seeded database: a session scratchpad script (not part of the repo) ran `OpenDispute`/`ResolveDispute` through four lessons (L1 100/0 not-yet-released, L2 0/100 not-yet-released, L3 trial 100/0 not-yet-released, L4 33/67 already-released, uneven price) and then `php artisan ledger:verify --no-interaction` → `"Ledger OK: every lesson sums to zero."`, against a database holding 4 lessons, 30 `ledger_entries` rows and 4 resolved disputes (`docs/CYCLE-LOG.md`, the 2026-09-29 06:19 entry, as corrected by the 06:42 NOTE — L4 is 16 `ledger_entries` rows, not the 14 the raw 06:19 entry states). This is the first `ledger:verify` run in the project's history against a non-empty DB with resolved disputes; the earlier `05:55` clean-suite gate run was against an empty DB (0 rows in `lessons`/`ledger_entries`) and is **not** dispute-path evidence, disclosed here to correct that run's scope rather than let it be cited as such. |
| "trial dispute defaults to 100% refund" | `ResolveDispute::prefillFor()` returns `[100, 0]` for `LessonType::Trial`, proven at two layers that actually exercise `prefillFor()` itself: `tests/Feature/Lessons/ResolveDisputeTest.php::prefills every R150/PRD §2.10 default: trial -> 100/0, everything else empty`; `tests/Feature/Filament/DisputeResourceTest.php::prefills 100/0 for a trial lesson's resolve form`. L3 in the seeded-DB proof above is **not** cited as evidence for this clause: that scratchpad script passed `100, 0` to `ResolveDispute` explicitly and never called `prefillFor()`, so L3 only proves a trial lesson dialled 100/0 settles zero-sum, nothing about the prefill default existing. |

Box ticked in `docs/CHECKPOINTS.md` on this evidence.

## Known limits (disclosed, not fixed)

- **No payment-gateway refund call — explicitly CP5-deferred scope, not a gap.** `docs/PLAN.md`'s
  R150 text says so directly: *"The gateway refund call is CP5, as for `provider_failure` (R122):
  the ledger records the refund owed; STATUS §6 carries the list."* `LedgerService::settle()` moves
  money inside the ledger (escrow → refund/tutor/platform accounts) but no `PaymentGateway::refund()`
  call is made against a real or fake gateway, and no `payments` row is created or updated by dispute
  resolution — the seeded-DB proof above created zero `payments` rows. This matches every other
  refund path in the codebase, not just this one: `grep -rn "\->refund(" app/` shows all four refund
  call sites (`CancelLesson.php:67,136`, `ChargeReservedLesson.php:253`, `LessonSettlement.php:22`)
  call `LedgerService::refund()`, never `PaymentGateway::refund()` — nothing in the app calls a real
  gateway refund yet, consistent with CP5's payment-gateway registry (ADR-018, Stripe as first live
  driver) still being unbuilt. The refund-owed list R150 requires is `docs/STATUS.md` §6 item AI: as
  of this report, it is empty by construction — no dispute has ever been resolved with real gateway
  money (only inside tests and this cycle's local-dev-DB scratchpad proof), so there is nothing to
  list yet; once CP5 lands, the list is every `disputes` row with `parent_refund_pct > 0`, joined to
  its lesson's `payments` row for the gateway reference.
- **`Goodwill` branch (`platformDelta < 0`) proven only by unit tests, not by the seeded-DB proof.**
  All four lessons in the `ledger:verify` proof (L1–L4) landed on `platformDelta ≥ 0` →
  `ReleaseCommission` or no platform leg at all; none exercised `platformDelta < 0` (a dial split
  where refund + tutor pay together exceed `price` — e.g. a high parent-refund percentage combined
  with a high tutor-pay percentage on the same dispute). That branch is covered only by
  `tests/Feature/Ledger/LedgerServiceTest.php`: the dedicated `it('settles a negative platform delta
  as goodwill', ...)` test (line 347) and the `'100/100'` case of the dial-matrix dataset (line 375),
  not by an end-to-end, non-empty-database run. L4, the proof's one uneven-price scenario, is
  `ReleaseCommission` (`platformDelta = 2010`, positive), not `Goodwill` — noted explicitly because
  an earlier scratchpad-script comment mischaracterised it as "goodwill" before this report was
  written; corrected here.
- **Tutor Earnings-page "on hold" bucket — not built, by a standing decision, not an oversight.**
  `docs/STATUS.md` §6 item AH: no Earnings page exists anywhere in the repo yet (CP5 scope);
  `disputed`/`settled` are real, queryable `LessonStatus` values left for CP5's Earnings page to use.
  In the meantime `tests/Feature/Lessons/ProgressReportTest.php::takes no report on a disputed lesson,
  and none on a lesson that is not waiting for one` (`tests/Feature/Lessons/ProgressReportTest.php:233`)
  is the closest existing evidence for PRD's broader "release pauses" language on a disputed lesson.
- **48h dispute window accepted as-is for v1 (R159, owner ruling 2026-09-29, closed).** `OpenDispute`
  stays anchored on `ends_at`; a lesson force-completed more than 48h late has no dispute route for
  the account holder. Accepted risk, not a gap left to revisit by default: the admin resolving such a
  lesson can still refund through the two `settle()` dials on their own initiative if the family
  complains, so no money is unreachable, only the account-holder-initiated 48h window. Revisit only
  if this actually happens on a real lesson (`docs/STATUS.md` §6 item AR, Owner action 17).
- **"Resolved" half of PRD §8's "Dispute opened / resolved | Both + admin" row is out of this
  sub-cycle's authorised scope**, per `DisputeOpenedNotificationTest.php`'s own docblock and
  `docs/PLAN.md`'s R150 line, which names only "opened" (tutor + admins). No resolved-dispute mail
  or bell exists yet for any party — parent, tutor or admin. Also out of scope: adding the parent to
  the "opened" notification (R150 names tutor + admins only, not the parent, even though the parent
  is the party who opened it and therefore already knows). Both carried to `docs/reports/8e.md`'s
  existing "Not built — CP8" row for this PRD §8 line, which this step does not close, only
  partially advances.
- **`no_show_student → completed_reported`'s traceability was checked, not assumed**: PRD §2.10's
  "student no-show → 0% refund, 100% tutor pay" default is *not* implemented as a `prefillFor()`
  branch, because no persisted record of *which* no-show path a `completed_reported` lesson arrived
  through survives to dispute-open time (`no_show_student` auto-advances to `completed_reported`,
  the same terminal-ish state a normal on-time lesson also reaches) — disclosed rather than guessed
  at; the admin sees the same empty-dial "no default" prefill for that dispute as for a quality or
  technical complaint, and must set both dials themselves reading the lesson's own history.
