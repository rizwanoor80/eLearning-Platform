# 8e — Notification centre and PRD §8 (R139)

Cycle 08, sub-cycle 8e, branch `cp/8e-notifications`. Scope: five database-notification "bells" (new
message, progress/trial report available, lesson confirmed, lesson cancelled, weekly-charge failed), a
bell with an unread count in both portals' headers (R135 polling, matching the existing 60s unread-message
badge — ADR-020, Reverb deferred to CP8), a `/notifications` list page, mark-read/mark-all-read, and this
report: every PRD §8 row, where it is met or which checkpoint owns it.

## What changed

| Area | Change |
|---|---|
| Schema | `notifications` table (Laravel's stock `database` notifications migration — `data` is `text`, not `json`/`jsonb`; see the idempotency-guard note below). |
| Notifications | `App\Notifications\Lessons\{LessonConfirmedNotification,LessonCancelledNotification,WeeklyChargeFailedNotification,ProgressReportAvailableNotification}`, `App\Notifications\Messaging\NewMessageNotification` — all `database`-channel only, `via()` returns `['database']`, no mail side (mail for these events already exists and is unchanged). |
| Listeners | `App\Listeners\Lessons\{RecordLessonConfirmedNotification,RecordLessonCancelledNotification,RecordWeeklyChargeFailedNotification,RecordProgressReportAvailableNotification}`, `App\Listeners\Messaging\RecordNewMessageNotification` — all `ShouldQueue`, queued alongside the existing mail listeners on the same events (`LessonStatusChanged`, `LessonChargeFailed`, `ProgressReportSubmitted`, `MessageSent`). |
| Idempotency | The database channel has no built-in dedup, unlike the mail side's `emailed_at`-claim columns. `RecordProgressReportAvailableNotification` guards a queue retry with an existence check keyed on `data->>'report_id'`, cast explicitly (`whereRaw("data::jsonb ->> 'report_id' = ?", ...)`) because `notifications.data` is `text` — Postgres has no `->`/`->>` operator on `text` (`42883`), so Eloquent's `where('data->report_id', ...)` json-path sugar cannot be used here. The other four listeners don't need a guard: `LessonStatusChanged`/`LessonChargeFailed`/`MessageSent` each fire once per real transition/event, and a duplicate row from a genuine queue retry is a cosmetic double-bell, not a money or safety issue, so only the one row-per-report case (which a retry could otherwise double *forever*, once per retry) was guarded. |
| Throttle (new message mail) | `App\Listeners\Messaging\SendNewMessageMail` — "at most one email per conversation per recipient per 30 minutes", an atomic `Cache::add("new-message-mail:{$conversation->id}:{$recipient->id}", true, now()->addMinutes(30))` (add-if-absent, not get-then-put, so two queued retries for the same message can't both pass). Independently keyed per recipient, so one party's own message never throttles the other party's. The bell (`RecordNewMessageNotification`) is unthrottled — every message gets a bell, only the email is rate-limited, per R139's own wording ("Emails unchanged except two new ones... at most one per conversation per recipient per 30 minutes"). |
| Body secrecy (invariant 8 / R134) | `MessageSent` already carried ids only (`messageId`, `conversationId`, `senderUserId`), dispatched after the DB transaction commits — no code change needed here, only a new test pinning it at the serialization layer (see below). |
| UI | `App\Http\Controllers\NotificationController` — `index` (Inertia `notifications/Index`, the current user's own notifications only), `markRead`/`open` (404, not 403, for another user's notification id — matches the existing conversation-access pattern), `markAllRead`. Routes: `GET /notifications`, `POST /notifications/{notification}/read`, `POST /notifications/{notification}/open`, `POST /notifications/read-all`. A bell icon with the unread count in `AppHeader.vue` (tutor portal) and `AppSidebar.vue` (parent portal), polled the same way and on the same interval as the existing unread-message badge (`UnreadCountsController`, R135) — no new polling mechanism introduced. |

## Known limits (disclosed, not fixed)

- **PRD internal inconsistency, disclosed per CLAUDE.md ("if you believe the PRD is wrong, say so"):** §8's table row reads "Report due (at lesson end, **+20h**)" (`docs/PRD.md:161`), but §2 describes the same feature as "Tutor is prompted at lesson end and by email. **Report due within 24h**" (`docs/PRD.md:67`) — a single immediate prompt plus a 24h deadline, not a second reminder fired 20 hours later. The build matches §2 exactly (`SendReportDueMail` fires once, immediately, on the transition into `completed`); no `+20h`-later nudge exists or is scheduled. Read `docs/reference/` for a tiebreak per CLAUDE.md's "if it conflicts with `docs/reference/`, the PRD wins" rule — no `docs/reference/` entry on this exists, so this is disclosed here rather than silently built either way; §2 is treated as authoritative until the owner rules otherwise, since it is prose rather than a possibly-transcribed table cell and it is what the implementation already matches.
- **Payout paid** and the **itemised VAT-line auto-charge receipt** are CP5 scope, not yet built; **Dispute
  opened/resolved** is CP8 scope, not yet built. Neither is in this step's authorised diff (R139 explicitly
  scopes 8e to the five bells + the two new/changed emails; building either would be scope creep past
  CP5/CP8's own checkpoints).
- **Rescheduled** has no v1 feature at all (scope guard: v1 is cancel + rebook, not an in-place reschedule) —
  the PRD row is N/A by design, not a gap.
- The bell's unread count uses the same R135 polling mechanism as the existing unread-message badge; Reverb
  push replacing both is CP8 scope (`ADR-020`), unchanged by this step.
- `notifications.data` being `text` rather than `jsonb` (Laravel's own stock migration) means any future
  bell that needs to query into `data` will hit the same `42883` operator error and needs the same explicit
  `::jsonb` cast — noted here so the next checkpoint doesn't rediscover it.
