## §3 What changed this cycle
- Earlier: ADR-030; **23a** registry and manager (`bdb6481`); **23b** `StripePaymentGateway`, webhook route and event table, two additive migrations (`b568853`); **23c** Stripe checkout with manual capture, saved card, `PaymentCapturedUnverified` (`509e654`). Full text: `git show fac7a24:docs/STATUS.md` §3.
- **23d (branch `cp/23d-gateway-refunds`, `18e9b65`):** when the ledger returns money to a parent, the gateway now gives it back. `RefundParentAtGatewayListener` (queued, 5 tries, back-off 30/120/600/1800 s) listens to `LessonStatusChanged` and, if the lesson has a Refund-account ledger entry, runs `RefundParentAtGateway`: for each entry without a recorded outcome it calls the payment's gateway `refund()` with the key `refund-<gateway_ref>-<entry id>` (amount `min(entry, payment)`), outside any lock, then in a short transaction records `refunds.<entry id>` in `payments.raw_response` and advances `payments.status` / `refunded_amount` (never downgrades). A permanent refusal (or no active gateway) is recorded as `refund_failures.<entry id>`, alerts admins (`PaymentNeedsAttention::REFUND_FAILED`, mail wording added) and is not retried; other failures propagate to the queue. `payments:retry-refunds` (hourly, `onOneServer`, `withoutOverlapping`) re-drives entries older than 10 minutes with no outcome; `--list` prints unconfirmed and refused entries for admins. `StripePaymentGateway::refund()` looks up an existing refund by metadata `idempotency_key` before creating one (Stripe forgets keys after 24 h) and maps card/invalid-request refusals to `PaymentCaptureException`. `ApplyPaymentWebhook` no longer raises a false `REFUNDED_AT_GATEWAY` alert when the ledger already returned at least the gateway total. The ledger is never reversed by a gateway failure. `LessonSettlement`, `ResolveDispute`, `CancelLesson`, `ChargeReservedLesson`, `LedgerService`, `LessonStateMachine`, the ledger migration, the interface and the fake were not changed. No migration. Tests: `GatewayRefundTest` (12), `StripeGatewayTest` extended (51); the R255 proof is in the CYCLE-LOG.
- **23d fix round 1 (review: 0 High, 1 Medium, 3 Low):** `StripePaymentGateway::refund()` rethrows `RateLimitException` and `lock_timeout` so the queue retries them (they were recorded as permanent refusals), and a refund Stripe reports `failed`/`canceled` is a refusal (`refund_failed` / `refund_canceled`); `RefundParentAtGateway` records only `PaymentCaptureException` as a refusal, so a gateway missing from the registry for a moment is retried; `payments:retry-refunds` alerts admins once per payment per day when the sweep itself fails. +5 tests; R255 proof (4 red with the fix planted out, 238 green restored) in the CYCLE-LOG.
- **23e (branch `cp/23e-receipts`):** a parent's receipts (R257). `GET /receipts` lists the account's paid lessons (payments it made with a gateway reference and status captured, partly refunded or refunded; 20 a page): date, lesson date, tutor display name, learner, amount in AED, the Stripe reference and any refunded total. `GET /receipts/{payment}` is one printable receipt (browser Print, `print:` styles): receipt number `R-<id>`, payer, tutor, learner, lesson time in the viewer's timezone, payment reference, the lesson fee, one line per ledger Refund entry (marked "returned to your card" once `raw_response.refunds.<entry id>` confirms it, else "being returned"), and the total paid net of refunds. **No VAT line** (D-04 open) and no email receipt (follows Postmark). A payment that is another account's, pending, failed or without a gateway reference is a 404 (`PaymentPolicy::viewReceipt`); guests go to login; tutors are outside the parent area. Dashboard gets a "Your receipts" link. Read-only: no ledger, lesson-state, payment-row or schema change. Tests: `ReceiptTest` (11). Presenter lives in `app/Services/Receipts/` (outside the frozen Payments directory). A refund line is returned / pending / refused; only returned refunds reduce "Total paid".
